## 1. 背景

V1.3 扩展应用平台的主要功能已经实现，包含 ZIP 安装、权限审批、不可变修订、iframe 沙箱、宿主 API、KV、文件传输、完整性检查、SDK/CLI 与管理 UI。对当前代码与最近 CI 的复核发现，仍需处理文件 API 的平台数据边界、网络权限执行、完整性校验、失败事务、运行资源清理、审计脱敏与 musl 交叉构建等问题。

本 SPEC 将这些问题定义为可单独实现、测试和验收的修复需求。它不代表问题已修复；完成状态必须以代码、回归测试和实际 CI 结果为准。

## 2. 目标与非目标

### 2.1 目标

1. 扩展应用即使获批使用文件 API，也不能读取、修改或删除 EdgeDesk 自身的认证状态、应用管理数据库、修订包、运行状态和其他明确列出的平台内部数据。
2. 网络权限和声明来源必须通过实际浏览器执行的策略生效，而不只是 UI 或 SDK 层校验。
3. 完整性校验覆盖活动修订的完整文件集合；历史修订问题不能误停用另一份健康的活动修订。
4. 安装、覆盖和重装失败时，原有应用数据保持完整；显式删除数据只在安装状态安全提交时发生。
5. 包安装、文件读取和资源服务避免随整个解压内容或单个超大资源无界占用内存；不静默更改已确认的产品资源限制决策。
6. 会话过期、权限失效和应用失效时，关联终端、传输任务、临时文件与锁均被清理。
7. 审计信息保留排障价值，但不把令牌、Cookie、查询参数中的秘密或未经清理的堆栈直接写入日志。
8. x86_64-musl 与 ARM64-musl 目标的依赖配置正确，完整 CI 矩阵重新通过。

### 2.2 非目标

- 不引入应用市场、数字签名、应用间通信、秘密存储或后端/脚本运行时。
- 不迁移认证、设置、终端或指标模块到 SQLite。
- 不重写现有文件管理、终端或桌面工作区；必须保持其既有行为。
- 不擅自引入固定 ZIP 总大小/文件数量上限、JSON-RPC 消息大小上限或扩展级调用速率/并发限制。当前风险清单将这些作为明确接受的产品取舍；若实现确实需要改变，必须另提 ADR/产品变更，不得在修复中暗中更改。
- 不把“保留弹窗和 opener 回调”解释为可以绕过获批的来源策略。若某项浏览器行为无法在现有决策下可靠约束，必须记录实际限制与残余风险，而非宣称已完全防护。
- 不改变现有网络风险决策：HTTP 来源、初始 URL 通过后浏览器自动跟随重定向，以及标准 opener 的残余风险仍按 ADR-0012/风险清单处理；本 SPEC 只修复实现对已批准权限与声明来源的执行偏差。

## 3. 需求

### SEC-01：扩展文件 API 的平台内部路径保护（发布阻断）

**files.manage** 仍通过既有 FileService/PathSandbox 执行，不得另造仅依赖字符串前缀或 **realpath** 的弱沙箱。扩展文件 API 必须拒绝访问平台内部受保护资源，包括但不限于：

- EdgeDesk 认证状态、密码状态、会话/Token 文件及其备份；
- 扩展 SQLite 数据库及其 WAL/SHM 文件；
- 扩展包、活动/历史 revision、安装临时目录和操作恢复元数据；
- 审计日志、平台运行配置和其他明确列入保护清单的内部状态文件。

保护必须在规范化后的路径解析和文件系统操作边界实施，并覆盖读取、写入、创建、覆盖、重命名、删除、目录列举及符号链接/硬链接别名场景。不得因默认 file root 为 **/** 而让扩展获得对平台私有状态的访问能力。管理员原有文件管理器的功能与配置语义必须保持不变。

**验收：** 对受保护路径的直接路径、路径变体、嵌套路径、符号链接以及可构造的别名执行读/写/列举/重命名/删除测试，均被拒绝且无文件变化；普通授权范围内文件操作仍通过；现有 PathSandbox 测试不回退。

### SEC-02：网络权限与来源策略必须真正生效（发布阻断）

- 外部 CSP source 只能在应用拥有有效的 **network** 授权且该来源属于当前修订声明的来源集合时加入。
- 首次审批、重新审批、升级、降级、回滚和创建新运行会话使用一致的授权规则。
- 升级新增或扩大外部来源时，必须进入明确的管理员复核流程；不得仅因应用此前获得过 **network** 权限就静默接受新的来源集合。
- SDK 的 **openExternal** 校验仅是开发辅助，不得作为安全边界。验证直接 **window.open**、**target=_blank**、表单导航及 iframe 导航的实际浏览器行为，确保它们不绕过当前已批准来源策略。
- 保留当前允许弹窗及 OAuth 回调的产品行为。若无法在既有 sandbox/CSP 设计下可靠限制某种导航，必须记录可复现的残余风险并提交 ADR，不得以 SDK 校验通过代替验证。

**验收：** 无 network 授权的应用不能通过外部脚本、图片、iframe、表单或连接请求使用 manifest 来源；授权来源生效，未授权/新增来源被阻止或进入复核；测试覆盖首次安装、升级来源扩展、禁用/重新启用和新建实例；浏览器 E2E 记录实际 CSP 与导航结果。

### SEC-03：完整性清单与资源服务保持一致

- 对修订执行完整性检查时，实际文件集合必须与平台保存的清单一致：缺失、修改和新增的未登记文件均视为不一致。
- 静态资源服务不得返回缺少完整性清单条目的文件。
- 检查历史修订失败不能自动使另一份健康的活动修订失效；只有受影响的活动修订确实不可信时，才隔离应用、撤销运行会话并关闭其窗口。
- 隔离、禁用、修复和审计结果在管理 UI、API 与数据库状态中保持一致。

**验收：** 对活动与历史修订分别覆盖文件修改、文件删除、新增未登记文件、清单条目缺失和合法修复；确认未登记资源返回错误；历史修订失败不会停止健康活动修订；活动修订异常会按既有安全契约立即失效。

### REL-01：安装/重装失败时保留原数据

当管理员选择重装且不恢复旧 KV 数据时，不得在新修订完成验证和状态提交前提前删除旧 KV。数据删除应与应用/revision 状态变更处于可恢复的事务边界；进程崩溃、文件移动失败、数据库事务失败或提交后清理失败时，恢复逻辑必须根据操作记录给出确定结果。

**验收：** 注入 ZIP 校验失败、磁盘写入失败、revision 移动失败、SQLite 事务失败和提交阶段崩溃；任何未成功提交的重装都必须保留原 KV 和原活动修订。成功重装且选择删除时，KV 才被清除；选择恢复时数据保留。

### REL-02：包处理与静态资源服务的内存占用

- 解压与哈希必须按块流式处理；不得把所有解压后的文件内容整体读入内存。
- ZIP 元数据、重复路径检测和完整性清单应避免不必要的重复副本；失败操作仍需可靠清理临时文件并保留原活动修订。
- 静态资源服务不得无条件把任意大小的资源完整复制到多个内存缓冲区。优先使用可验证的流式/分块响应；如当前 HTTP 层无法支持，需提交具体技术证据和 ADR/后续设计，明确剩余内存风险。
- 保持“不设固定包大小/文件数上限”的现有决策；不得通过悄悄加入固定上限来让测试通过。仍须保留结构校验、磁盘可用空间检查、失败清理与原子激活。

**验收：** 使用多文件、大文件和高压缩比测试样本，记录安装/静态服务过程的峰值内存；证明解压内容大小不会线性转化为全量常驻内存。覆盖磁盘不足和中断场景；没有未经批准的新固定配额。

### REL-03：运行时失效清理完整且幂等

运行会话因过期、应用禁用、升级、卸载、修订隔离或显式关闭而失效时，统一执行会话清理流程，包括会话记录、关联终端、上传/下载任务、临时文件、文件锁和事件订阅。锁内只更新状态，不得因关闭终端回调引发重入死锁；资源清理需要幂等。

**验收：** 分别触发 TTL 过期、并发请求发现过期、禁用、升级、卸载、完整性隔离与进程恢复；关联终端被关闭，临时传输和锁被释放，重复清理无崩溃/死锁/残留。

### SEC-04：应用错误上报与审计日志脱敏

应用提供的错误消息、堆栈、URL 和资源信息均视为不可信输入。日志必须限制长度并进行结构化编码；移除 URL 查询参数/片段中的敏感值，脱敏常见的 Token、Cookie、Authorization、API Key 和密码字段。除排障必需且已脱敏的信息外，不记录完整请求正文或任意文件内容。

**验收：** 用包含 Cookie、Bearer Token、API Key、密码、URL query/fragment、超长字符串和多行堆栈的样本触发错误上报，审计文件中不存在原始秘密，JSONL 结构仍有效，普通错误仍可定位。

### BUILD-01：恢复 musl 交叉构建与完整 CI 矩阵

为 x86_64-musl 和 ARM64-musl 构建提供与目标工具链匹配的 ZLIB 头文件、库和 CMake 查找路径。依赖必须可重复获取/构建，不得意外链接宿主机 glibc 或宿主机库。保持 GCC 15、静态链接目标与既有依赖锁定。

**验收：** x86_64-musl、ARM64-musl 两个失败目标均配置和链接成功；检查最终二进制依赖符合静态目标；frontend、host-build、gcc15-embed、x86_64-musl-static、arm64-cross 全部通过。若目标 job 还负责额外测试，必须保留其原有验证步骤。

## 4. 通用完成标准

- 每个修复都有针对具体失败模式的自动化回归测试，不只增加人工检查步骤。
- 保留现有功能、API 兼容性和既有安全控制；若必须改变已确认决策，先提交 ADR。
- 路由层只做协议适配；文件路径边界放在 **src/file/** 与统一 PathSandbox/FileService，扩展业务逻辑放在 **src/extensions/**，审计脱敏放在审计/安全层，不能将核心校验散落在 UI。
- 每个 PR 运行 **scripts/test-fast.sh**；涉及运行时/文件安全/生命周期的 PR 运行 **scripts/test-pr.sh**；涉及 CMake、工具链、依赖的 PR 重新运行 L2 全矩阵。
- 更新 **docs/testing.md**、**docs/extension-platform-contracts.md** 或风险清单中的相关状态，清楚区分“已接受风险”“已修复缺陷”和“未验证”。
- 不得把本 SPEC、Issue 创建或本地单测通过当作修复完成；以合并后的 CI 与测试证据为准。
