# SPEC-0011：原生应用包与后端运行时

- 状态：**宿主实现完成（x86_64 glibc 已验证；生产发布门槛未满足：ARM64/ARM32、musl、真实 root 身份切换与 init/reboot 未验证）**
- 日期：2026-10-23
- 关联基线：[SPEC-0007：扩展应用平台](0007-extension-applications.md)、[SPEC-0008：扩展平台加固](0008-extension-platform-hardening.md)、[SPEC-0009：Process Supervisor](0009-process-supervisor.md)、[SPEC-0010：Supervisor 安全与可靠性加固](0010-process-supervisor-hardening.md)
- 关联 ADR：[ADR-0011](../adr/0011-extension-runtime-and-packages.md)、[ADR-0012](../adr/0012-extension-security-and-communication.md)、[ADR-0015](../adr/0015-process-supervisor-architecture.md)、[ADR-0016](../adr/0016-process-supervisor-security.md)、[ADR-0017](../adr/0017-root-operations-profile.md)、[ADR-0018](../adr/0018-native-application-packages.md)
- 实施计划：[SPEC-0011 实施计划与 Ticket 拆分](../tasks/0011-native-application-packages.md)

> 本 SPEC 在现有静态 Web 扩展基础上增加可选的原生后端能力，不替换现有 Web 运行时。本文获批不代表功能已实现；实现状态以代码、自动化测试和 docs/testing.md 中的实际证据为准。

## 1. 目标与范围

EdgeDesk 扩展应用包继续使用 ZIP 和现有 manifest.json。纯 Web 应用保持现有行为；需要本地系统能力的应用可以在同一个包中携带一个原生 ELF 后端。

V1 必须实现：

- 兼容现有纯 Web 应用包，并支持可选的单个原生后端。
- 安装时验证包结构、文件路径、SHA-256 和 ELF 架构；安装过程不得执行包内程序或脚本。
- 复用 Process Supervisor 管理后端启动、停止、重启、运行用户、用户组和开机自启。
- 通过 HTTP over Unix Domain Socket 提供后端 API；Web 前端只能通过宿主 JSON-RPC/MessagePort 桥接访问自己的后端。
- 程序文件与持久化数据分离；卸载默认保留数据。
- 采用尽量简单的覆盖升级，不为原生后端实现多版本切换和自动回滚。
- 提供应用管理界面、SDK/CLI 契约、示例与跨架构验收。

## 2. 明确的非目标

V1 不实现：

- 一个应用包含多个后端进程。
- Shell 命令字符串、脚本、Node.js/Python 等服务端运行时。
- 强制数字签名、发布者证书体系或公共应用市场。
- 容器、namespace、seccomp 或新的进程沙箱。
- 后端健康检查协议、WebSocket 代理、流式响应代理。
- 应用间后端调用、服务依赖图或应用市场依赖解析。
- 原生后端的历史版本目录、版本指针切换或自动回滚。
- 每个应用单独生成 systemd、OpenRC 或 BusyBox init 服务单元。

## 3. 与现有 Web 扩展的兼容规则

1. backend 字段缺失时，应用完全按 SPEC-0007 的纯 Web 应用处理，不创建 Supervisor 服务，也不执行 ZIP 中任何可执行文件。
2. 保留现有 manifest 核心字段、宿主 API 兼容性检查、权限审批、iframe sandbox、MessagePort、WindowManager、KV、文件 API 和现有审计机制。
3. 现有 Web 静态资源仍使用 SPEC-0007 的 revisionId、版本化 URL、不可变缓存和既有升级机制。
4. 新增原生后端使用应用专属的稳定程序路径并按原目录覆盖升级；不为后端二进制保留历史版本或自动回滚。
5. 应用数据默认保留是最新确认的统一卸载策略。管理界面默认保留用户数据和平台 KV 数据；彻底删除数据必须通过独立的清理操作完成。
6. 不得把本 SPEC 解释为已实现后端运行时，也不得将现有 Web-only 测试结果当作原生后端验收证据。

## 4. 应用包与 manifest

### 4.1 包布局

ZIP 包沿用现有 manifest.json 和 Web 静态资源。含原生后端的包额外携带一个 ELF 可执行文件，例如：

- manifest.json：现有字段与可选 backend 配置。
- index.html 及前端构建产物：沿用现有 Web 包约定。
- backend 可执行文件：包内相对路径指向一个原生 ELF 文件。

每个原生包只包含一个目标架构的后端程序。ARM32、ARM64、x86_64 分别构建和发布。纯 Web 包不受设备 CPU 架构限制。

### 4.2 可选 backend 字段

在现有 manifest 中增加可选 backend 对象：

| 字段 | 类型 | 规则 |
|---|---|---|
| backend | object，可选 | 缺失表示纯 Web 应用 |
| backend.executable | string，必填 | 相对于包根目录的可执行文件路径 |
| backend.args | string array，可选 | 默认空数组；每个元素是一个独立 argv 参数，不进行 Shell 展开 |

不允许应用包声明运行用户、运行组、root 标志、Socket 绝对路径或宿主数据目录。这些值由 EdgeDesk 管理员和宿主运行时管理。

校验规则：

- 路径必须是包内相对路径；拒绝绝对路径、路径穿越、符号链接、重复路径和非普通文件。
- 目标必须是可执行 ELF 文件；拒绝脚本、非 ELF 文件和不可执行文件。
- 安装器检查 ELF 目标架构是否与设备匹配；不匹配时拒绝安装。
- 不经 Shell 启动。可执行文件与参数数组分别传递给 Process Supervisor。
- 不允许 backend 对象声明多个进程。
- 旧 manifest 未包含 backend 时必须继续通过现有校验。

### 4.3 完整性与来源

- 复用现有 ZIP 安全检查和逐文件 SHA-256 完整性清单。
- 不强制数字签名。SHA-256 用于检测内容变化，不证明发布者身份。
- 管理界面明确提示：未签名包的发布者身份未经验证。
- 安装前完整校验 ZIP、manifest、ELF 和架构；校验失败不得修改当前活动应用或启动任何程序。

## 5. 安装与文件布局

### 5.1 安装

安装流程复用现有应用包管理器的流式 ZIP 校验、路径安全、完整性清单和 SQLite 操作记录。

1. 将包上传到临时区域。
2. 校验 ZIP、manifest、路径、重复文件、符号链接、SHA-256、ELF 类型与架构。
3. 准备 Web 静态资源修订和原生后端文件。
4. 提交应用元数据和后端服务映射。
5. 安装完成后后端必须处于 STOPPED，且开机自启关闭。
6. 安装阶段不得执行后端，不运行安装脚本，不允许包内程序隐式修改系统配置。

任一步骤失败时，不得把半成品登记为可启动应用。复用现有操作记录与恢复机制清理临时文件。

### 5.2 程序文件、数据与运行目录

- 原生可执行文件位于应用专属的稳定程序目录；后端升级时覆盖该路径。
- 程序目录与持久化数据目录分离。数据目录由宿主配置，默认位于 EdgeDesk 应用数据根目录下的独立 appId 子目录。
- 运行数据目录通过 EDGEDESK_APP_DATA_DIR 环境变量传给后端。
- Socket 位于宿主创建的每应用运行目录中；宿主通过 EDGEDESK_APP_SOCKET 环境变量传入完整 Socket 路径。
- Socket 路径、父目录权限和 Socket 文件权限必须同时允许指定后端身份创建/监听，并允许 EdgeDesk Web 后端连接；权限无法安全建立时必须拒绝启动。
- 安装程序目录不得对普通后端运行用户开放写权限。root 身份按管理员显式配置的实际权限处理。
- 目录创建、属主修改和权限修改必须限制在 EdgeDesk 拥有的专用目录中，使用 SPEC-0010 要求的安全路径处理；不得对任意路径直接 chmod/chown。
- 不允许 manifest 指定任意数据目录或 Socket 路径。

## 6. 后端进程生命周期

### 6.1 Process Supervisor 集成

应用管理器为每个含 backend 的应用生成一个 Supervisor 服务，并保存稳定的 appId 到 serviceId 映射。

- 服务执行文件路径由安装器解析为绝对路径，参数保持 argv 数组。
- 工作目录使用应用专属程序目录；业务持久化文件必须使用 EDGEDESK_APP_DATA_DIR。
- 运行用户和用户组由管理员指定，不能由 manifest 或包内程序自行决定。
- 可以选择 root；必须复用现有 Process Supervisor 的显式 allow_root 约束。这里不新增另一套应用级 root 授权流程，但不得静默以 root 运行。
- 默认不开机自启；开机自启是独立设置，与手动启动/停止分开。
- 安装不启动后端。管理员必须显式启动应用。
- 复用现有 Supervisor 的生命周期状态、日志、重启策略和 init 适配。V1 不新增应用健康检查协议。
- Supervisor 的 RUNNING 只代表进程存在，不代表 HTTP API 已就绪或业务健康。
- 扩展管理器拥有该服务配置。进程管理界面可以显示扩展服务状态，但不得让普通编辑路径意外覆盖应用管理器生成的可执行路径、参数或身份配置。

### 6.2 管理操作

应用管理界面提供：

- 配置运行用户与用户组。
- 启动、停止、重启。
- 独立启用/禁用开机自启。
- 展示 Supervisor 进程状态、最近退出信息和日志入口。
- 展示运行身份、架构、后端可用性错误及升级失败状态。

运行身份未配置、身份解析失败、程序文件不可执行、架构不匹配、Socket 权限无法建立或 Supervisor 不可用时，不得报告启动成功。

### 6.3 开机恢复

开机自启复用 Supervisor 已有 autostart 与 init 适配能力。应用默认 autostart=false。应用安装、手动启动和停止不得隐式修改开机自启设置。

重启恢复必须尊重持久化的 desired_state；手动停止的服务不得仅因 Supervisor 重启而自动恢复运行。该要求依赖 SPEC-0010 对生命周期持久化与恢复语义的修复。

## 7. 前端到后端的通信

### 7.1 访问路径

Web 前端继续在现有 iframe sandbox 中运行，并通过专属 MessagePort 使用 JSON-RPC 2.0 宿主 API。新增 backend.request 方法族，由宿主代理将请求转发到当前应用绑定的 Unix Domain Socket。

前端不得：

- 直接访问 Unix Socket。
- 指定 Socket 路径、任意主机、端口或完整 URL。
- 访问其他应用的后端。
- 通过后端代理绕过现有文件、终端或其他宿主 API 权限。

宿主必须从当前已验证的运行实例确定 appId 和 Socket，不能信任请求参数中的 appId。

### 7.2 V1 请求契约

backend.request 至少接受：

- method：允许的 HTTP 方法，例如 GET、POST、PUT、PATCH、DELETE。
- path：以 / 开始的应用内相对路径，不允许完整 URL 或路径穿越。
- body：可选 JSON 值。
- contentType：V1 默认 application/json。

宿主通过该应用专属 UDS 发送 HTTP 请求，并返回 HTTP status、允许返回的响应头和 JSON body。宿主不得将任意客户端提供的 Host、Connection、Upgrade 等 hop-by-hop 头透传给后端。

V1 只承诺常见 JSON API 请求/响应，不支持 WebSocket、任意 TCP 代理或流式文件传输。大文件操作继续使用现有宿主文件 API。

### 7.3 访问控制与错误

- 默认只允许应用自身的前端访问自身后端；V1 不实现跨应用调用。未来跨应用能力必须通过单独的 manifest 权限与审批决策引入。
- 调用必须经过现有 MessagePort 握手、运行实例、权限快照和会话状态检查。
- 不运行、Socket 不存在、连接拒绝、权限错误、响应格式无效时，返回稳定、可诊断的宿主错误。
- 关闭窗口、禁用或升级时，旧实例的 MessagePort 失效。
- 不增加独立健康检查协议；前端调用失败时显示后端不可用错误，不能把 Supervisor RUNNING 等同于 API 可用。

## 8. 升级与失败处理

### 8.1 升级流程

1. 上传新 ZIP 并完整校验包、manifest、SHA-256、ELF 和目标架构。
2. 校验失败时保持现有应用与进程不变。
3. 关闭应用运行实例并停止原生后端。
4. 将后端二进制覆盖到稳定程序路径；不保留原生后端历史版本，不自动回滚。
5. 后端文件替换和元数据更新成功后，更新应用版本信息并激活新 Web 静态资源修订。
6. 升级成功后保持后端停止；是否再次启动由管理员决定。
7. 在停止后端后发生的覆盖或元数据提交失败，应用必须保持停止，显示 UPGRADE_FAILED 和明确错误，不得报告升级成功或自动启动可能不匹配的版本。

V1 不提供原生后端二进制自动回滚。管理员可以重新上传旧包进行人工恢复。Web 静态资源继续使用现有版本修订与不可变 URL 机制，不得原地覆盖已发布 revisionId 对应的资源。

### 8.2 数据兼容

- 升级和后端覆盖不得删除应用数据或平台 KV 数据。
- EdgeDesk 不解释应用业务数据格式，不承诺自动回滚业务数据。
- 应用负责自身数据结构迁移；V1 不增加通用迁移框架。
- 发生升级失败时保留数据与诊断记录，等待管理员处理。

## 9. 卸载与数据保留

- 卸载前必须先停止后端；若无法确认服务已停止，卸载操作失败并保留程序文件，避免删除仍在运行的程序。
- 成功卸载时删除原生程序文件、Web 应用活动记录和由扩展管理器创建的 Supervisor 服务配置，并撤销应用权限。
- 默认保留应用持久化数据和平台 KV 数据。
- 彻底删除数据是独立的管理员操作，必须显示 appId 与数据范围并要求明确确认。
- 应用数据清理只允许作用于该应用的专用数据目录与 KV 命名空间，不得跟随符号链接或删除目录根以外的数据。
- 保留必要审计记录；卸载不得删除历史审计。
- 同一 appId 重新安装时，恢复已有数据必须由管理员明确确认，且应用权限重新审批。

## 10. 安全边界与已接受风险

- 应用包不要求数字签名；SHA-256 不能证明发布者身份。
- V1 不实现额外进程沙箱。应用权限由所选 Linux 用户、用户组、文件权限和现有 Supervisor 配置决定。
- 管理员指定 root 时，后端拥有主机级权限。不能把 root 扩展视为受限插件；恶意或有漏洞的 root 后端可能控制整台设备。
- 不允许包内安装脚本、Shell 命令字符串或自动执行逻辑。
- 宿主只代理到应用绑定的 UDS，禁止由前端提供任意 Socket/URL，以避免代理被用作访问其他本地服务的通道。
- 应用程序目录、数据目录和运行目录必须分离，并在文件系统边界执行权限检查。
- 不新增应用间通信、秘密存储或后端级访问其他应用数据的能力。
- 由于没有进程沙箱，无法阻止具有相应 OS 权限的后端主动打开 TCP 端口、访问主机文件或执行其他系统调用；这是管理员选择运行身份时必须理解的风险。

## 11. 测试与验收

### 11.1 兼容性

- 现有 Web-only 包无需修改 manifest，仍可安装、审批、启用、打开、升级、降级和卸载。
- 现有 iframe、MessagePort、权限、WindowManager、KV、文件 API、缓存和恢复测试通过。
- Web-only 包不得意外生成或启动 Supervisor 服务。

### 11.2 包与安装

- 有效 ELF 后端包通过；脚本、非 ELF、不可执行文件、错误架构、绝对路径、路径穿越和符号链接均拒绝。
- 安装不执行后端，安装完成后服务 STOPPED 且 autostart=false。
- SHA-256、ZIP 损坏、重复路径、磁盘不足和安装中断均有失败测试。
- 包校验失败不得改变现有应用状态。

### 11.3 生命周期

- 管理员配置运行身份后，可以启动、停止和重启后端。
- Supervisor 服务配置使用绝对可执行路径和 argv 数组。
- EDGEDESK_APP_SOCKET 与 EDGEDESK_APP_DATA_DIR 由宿主传入，且不允许 manifest 覆盖。
- 开机自启可独立启用/禁用，默认关闭。
- Supervisor 停止、崩溃恢复、SQLite 写失败、root 身份切换和 init 适配必须使用真实测试证据。

### 11.4 通信与隔离

- 应用前端通过 JSON-RPC/MessagePort 调用 backend.request 后，经 UDS 完成 HTTP 请求/响应。
- app A 不能通过请求参数访问 app B 的后端或任意本地 URL。
- 未启动、Socket 权限错误和后端返回无效响应时返回明确错误。
- 浏览器不可直接访问后端 Socket 或 EdgeDesk 为后端创建的 TCP 端口。
- 关闭/禁用/升级后旧运行实例不能继续发起代理请求。

### 11.5 升级、卸载与数据

- 升级前校验失败时旧应用保持不变。
- 覆盖失败时应用保持停止并标记失败，不自动回滚。
- 升级不删除数据；卸载默认保留数据。
- 独立清理操作只删除指定 appId 的数据，并有确认与审计。
- 数据目录、Socket 目录和安装目录的路径安全测试通过。

### 11.6 发布门槛

- SPEC-0010 中进程组身份校验、残留后代清理、目录权限、持久化失败和恢复语义等 P0/P1 问题必须关闭后，才允许把原生后端包标记为可供生产使用。
- 至少在实际可用环境验证 x86_64 与 ARM64；ARM32 未执行时必须标记未验证。
- 必须记录实际构建/运行环境、内核、libc、测试命令和结果。交叉编译成功不能替代目标环境运行验收。
- 现有文件管理、终端、认证、设置、桌面和 Web-only 扩展回归必须通过。
